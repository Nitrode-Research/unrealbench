# Combo discovery interface

`UComboDiscovery::DiscoverCombos(Battle, Request)` searches for combo routes from the battle's current situation and returns them as playable trials. `UComboDiscovery::ValidateTrial(Battle, Trial, OpponentInput)` replays a trial from the current situation, supplying `OpponentInput` to player 2 on every frame, and judges whether it completed. Both take a live `ANightSkyGameState` in the battle phase whose player 1 is not stunned, and receive ordinary button and direction bitmasks; a null battle is outside the contract. As an integration constraint, they advance the battle only through its ordinary frame update (`UpdateGameState`). Both leave the battle's gameplay state exactly as they found it: frame number, health, positions, states, stun, combo counters, input history and everything else that decides later frames, so stepping on afterwards is unaffected. Presentation state (particles, audio, widgets) is exempt, and the public `LocalFrame` counter is deliberately not restored: it advances by exactly the number of frame updates the call ran. The declarations live in `Plugins/NightSkyEngine/Source/NightSkyEngine/Battle/Lab/ComboDiscovery.h`.

Frames count from 1 for the first frame advanced after the situation. `FComboSearchRequest` declares the move list (`FComboMove`: the state's gameplay tag and the single-frame input that begins it, in ranking order), `MaxSteps`, `MaxFrames` (the last hit must register on or before it), `MaxResults`, `MaxSimulatedFrames` (frame updates the search may run in total, over all branches, every update counting) and `OpponentInput` (supplied to player 2 on every simulated frame). `FComboSearchResult` carries the ranked `Trials` (highest `TotalDamage` first) and `bComplete`. Each `FComboTrial` lists its `Steps` (`FComboStep`: state, move index into the request's list, `Kind` of `Cancel` or `Link`, `BeginFrame`, `HitFrame`, `Damage`), `TotalDamage` (the sum of the steps' `Damage`), and `Inputs`, one player 1 input per frame from frame 1 through the last hit frame. Idle, for both kinds, means player 1's primary state has `EStateType::Standing` at the end of the frame under neutral input. `ValidateTrial` reads only `Inputs` and each step's `State` and `Damage`; `MoveIndex`, `BeginFrame`, `HitFrame`, `Kind` and `TotalDamage` are ignored. `FComboTrialReport` returns `bCompleted`, `FailedStep` (-1 on success) and `ObservedDamage` (health the opponent lost during the replay, including to the action in progress at the situation; on failure, up to and including the failing contact). The neutral input is `INP_Neutral`; input values are `EInputFlags` bitmasks.

`FNSE025Battle` (`Plugins/NightSkyEngine/Source/NightSkyEngine/Fixtures/NSE025Fixture.h`) is a neutral two-fighter battle for authoring attacks in native code. `AddMove(FNSE025MoveSpec)` gives the attacker one attack; the i-th added move is the state `FNSE025Battle::MoveTag(i)` (eight tags exist) and the spec's `Input` is the button that begins it, so give each move its own button. `SetMove(i, Spec)` rewrites an added move's parameters in place and is legal after `Start` while the attacker is idle. A move runs `Startup` frames, then an active hitbox spanning `Reach` units in front of the attacker for `Active` frames, then `Recovery` frames, then returns to the stand state by itself; it lands one hit per activation unless a nonzero `MultiHit` re-arms the hitbox on that action frame for another contact, and a blocked hit removes no health. Hit values (`Damage`, `Hitstun`, `Untech`, `Hitstop`, `Pushback`, prorations, `MinimumDamagePercent`), the hit action (`AirHitAction`, the move's reaction against grounded and airborne defenders alike; the air actions launch, setting `AirPushbackY` and `Gravity` as the arc and `Untech` as the launch stun) and cancel authoring (`ChainCancels` by move index, `CancelFrom`, the action frame from which those options are offered, `MaxChain`, `bReverseBeat`, `bFollowup`, `Type`) map onto the engine's ordinary state and hit data; moves hit downed opponents. `Attacker->CanReverseBeat` lets the attacker chain normals freely; it is rollback state, so set it before `Start`, which keeps the value as part of the situation.

`Start(AttackerX, DefenderX)` places both fighters on the ground facing each other, runs one neutral frame, and remembers the situation; calling it again first returns to the previous situation, so a reused battle starts clean. The walls are the stage bounds at +-3200000 and a fighter stops 85000 inside them, so a fighter placed at +-3115000 is in the corner. `Reset()` returns to the remembered situation; `Step(Input1, Input2)` advances one real battle frame; `Frame()` counts frames since `Start`. The defender stands idle, blocks a hit only while idle and holding back, and enters ordinary hitstun or blockstun otherwise; air hit actions put it in the engine's universal launch states, where it can act by teching once its untech expires while airborne, except that a knocked-down defender cannot act, airborne or not (`TechInput()` is the raw input that techs, held); `GuardInput()` is the raw input that makes it hold back for its facing. `AttackerBegan(MoveIndex)` is true at the end of the frame on which that move began (a move lasting at least one action frame, which every authored move does), and `DefenderInHitstun()` reads the defender's stun state type (`Defender->CheckIsStunned()` is the engine's own "cannot act" query, which is also true on the frame a hit or a block lands and while the defender is in blockstun). The fixture never implements searching or validation; `Game`, `Attacker` and `Defender` expose the ordinary engine objects.
