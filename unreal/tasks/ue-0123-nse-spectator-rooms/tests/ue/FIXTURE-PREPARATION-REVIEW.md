# Ordinary native battle preparation before process-room start

This test-only delta supplies the native battle that the authored process fixture previously created only through an explicit `battle` command, its loading callback, or replay. The fixture lobby uses `AGameStateBase`; loading the selected content alone does not construct a battle. Protected delta45's first CombinedLifecycleFuzz start stayed publicly inactive while the process continued responding. These facts establish a fixture compatibility concern, not the cause of candidate behavior.

The three process drivers now issue `prepare-battle` after accepted character/stage selection and existing invalid-content/start checks, before their final readiness and successful-start commands. The command uses the fixture's existing ordinary server-travel and deferred actor-spawn path. Its normal `FinishSpawning` begins native initialization. If the players are still absent, normal actor ticks remain available and later worker ticks retry preparation against the current world. Once both native players exist, it calls the public `USpectatorRoom::BindBattle`. Missing-player diagnostics are guarded during preparation. Both-player existence permits this association only; it does not stop normal ticks or claim that initialization is complete. Normal ticks remain available throughout prestart and pending start, including replacement actors reached by a later loading callback. It does not set public active state, match identity, readiness, history, input, or elapsed room time. No fighter input or manual simulation step is sent during preparation. The native automation source is absent from this archive; staged fixes 47/48 remain separate.

A private fixture marker permits a later ordinary `TravelToVSInfo` callback to reuse exactly the prepared world and actor. Reuse also requires the currently selected stage/map, both character lists/classes, configured random seed, round timer/count/start delay, and training setting to match. It does not impose that the candidate dispatch this callback, and does not compare or overwrite its runner choice. Explicit next preparation clears the marker and uses ordinary replacement travel, even for the same stage. Replay, invalid actor, changed world, or changed configuration invalidates reuse. Pending travel is completed through the existing worker tick against its current game-instance world; no old-world pointer is ticked manually.

The driver waits for the current preparation serial, a matching configured seed, and the associated prepared actor with both observed native players. Its observed native frame is telemetry only: ordinary initialization may advance it before the implementation establishes public match frame0 on successful start. The fixture never resets or rebaselines native state. It then waits for current owning channels, nonempty current memberships, and the selected map. If preparation requested travel, each participant must independently report an increase in its own game instance's completed-map-load count. Membership generation equality is not required. Each of these two fixture waits is bounded by 60 seconds; existing public-start 30-second observation bounds and leaf/global caps remain unchanged. These are test setup bounds, not a public maximum initialization latency.
