# Native fixture travel and authority association review

This test-only proposal addresses the delta50 native fixture's synchronous input loops and its cached/first-actor selection. It is not a candidate implementation fix. The immutable delta50 inputs, prior approved archives, process fixture/organizer correction, and zero-input interruption body remain separate.

## Public success precedes live setup

The existing active/new-match successful-start assertion runs as soon as the public observation succeeds. RealBattleDelayedHistory, FreshOfflineReplay and RenderedDVR also run their original `frame zero boundary` and `zero bytes obey delay` checks there, before advancing travel. The first successful public match identity and the fixture start-clock snapshot are recorded. Later setup must retain that exact identity, and continuations use the recorded identity for existing input/release checks. The room clock and match identity are not reset. The original `zero releases` check still runs at original start+D. No fighter input command is sent while awaiting this setup. The separate eight-case zero-input test body is byte-identical to delta50; its exported-frame decode failure remains unresolved.

## Exact authored actor and one association per setup event

Each native authority fixture explicitly opts in after its original configured `AReplayFixtureBattle` construction. An optional normal `TravelToVSInfo` callback performs ordinary server travel to the selected stage, using a test-owned native GameMode as the substitute for the fixture loading-screen content. It preserves the selected assets and battle configuration. The test does not require that callback: the initial explicitly supplied actor remains usable until a real replacement setup occurs. Replay and fixtures that did not opt in use the original callback unchanged.

The new GameMode supplies the exact `AReplayFixtureBattle` it created. The completion flag is set only at the end of the original fixture BeginPlay body, after original base/HUD/light/audio initialization. It is an authored construction event, not a promise that every later room initialization operation has finished. Once that event and the original player observations exist, the fixture calls public `BindBattle` once for that initial or replacement actor and records it weakly. A weak actor and setup generation are captured before public dispatch. The provisional witness is hidden until dispatch returns; nested replacement setup wins over an older returning binding. A repeated callback for the same actor does not rebind. The return path revalidates the weak actor/current world without using the old raw pointer. World replacement, actor destruction and replay invalidate the direct-observation witness. No actor enumeration or arbitrary game-state selection establishes this association. No input, native frame, room state, history, seed or configuration is reset or rebased.

## Stock travel ordering and bounded latent frames

Only the standalone context created and manually advanced by this native fixture is pumped. One latent Update performs at most one advancement: save the prior context handle, select the fixture context/current GWorld, call public `TickWorldTravel`, reacquire the context/current world, then tick that world. Restoration resolves the prior context's current world. Missing contexts are nullable; no stale world/reference is reused across travel. Pending status includes world BeginPlay, NextURL, TravelURL, PendingNetGame and seamless transition. There is no recursive engine tick, core ticker, or task-graph pump.

The original 240-, 600- and 40-pair loops are latent phases. Each pair is submitted once and public `Room->BattleTick(OneFrame)` is called once for that pair. The phase yields before reading direct native outcomes, reacquires the witnessed actor, and permits ordinary pending travel/native initialization work. If the active actor has not progressed since that submitted pair, it permits further ordinary fixture-world work without repeating either input or the public tick. Progress is a scheduling boundary; all original native/control/history checks still decide correctness. The pause test follows the same single-dispatch/yield path and deliberately expects a frozen frame.

Startup retains its 30-second fixture bound. Each finite gameplay sequence has a 30-second wall-time budget for reaching any needed pending/progress boundary; elapsed time is checked whenever it would wait. Original pair counts, virtual clock changes, deciding-frame release and native assertions remain. Existing leaf/global protected-run caps remain unchanged. These are harness bounds, not a contractual maximum implementation latency.

Positive inputs refresh public current membership/role/assignment observations. The known organizer may own a seat while retaining organizer role; ordinary peers still require fighter role, and both assignments must be nonempty and distinct. Historical stale-match/spectator injection checks remain. Widget roles/memberships and weak connection/world handles are captured before the initial binding and start dispatch. The current world is reacquired after binding before controls reconnect through their ordinary actions. Native initial/successor start dispatches also require a fresh inactive observation, so preparation binding alone cannot satisfy successful start; legitimate replacement binding after accepted start remains allowed. Two widget comparisons of old assignment generation strings become current owned-seat checks, alongside their existing membership and role assertions.

## Validation and limits

Host checks parse all three C++ files after Unreal macro normalization and compare balanced original assertion expressions. There are 292 original assertion call sites: 290 retain their expressions (allowing phase-local aliases), while the two assignment-generation comparisons are replaced as described above. The v4 draft contains 307 calls in total, including the new inactivity and first-success identity/clock guards. The zero-input body is byte-identical. The host Python scheduling/preparation tests are run separately; they do not validate native execution.

The change does not replace direct live-authority evidence with replay reconstruction or prediction getters. It does not prove that a candidate will complete initialization, preserve an association, accept/confirm pairs or advance the correct native battle. It does not repair or close the process-driver startup failures or the zero-input decode failure. Protected UE compile/runtime is required; no local Unreal build/run was performed.
