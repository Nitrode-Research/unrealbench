# Pending-start compatibility review

This patch removes immediate-success assumptions from existing accepted-start tests. A successful start must still establish a fresh match and reproducible initialized frame 0. Preparatory responses may remain pending. Rejected-start checks and the approved zero-input interruption witness retain their assertions.

The previous `pending-start-compatibility-review.zip` is a superseded draft. It manually pumped the core ticker inside a synchronous test and retained battle references across possible travel. It must not be integrated. The immutable v2 archive was rejected because its tick guard also stopped uninitialized replacement actors and its widget checks required old membership-generation tokens after reconnect. The v3 code passed independent test-constraints review for protected compile/runtime. The current archive is `pending-start-latent-compatibility-review-v4.zip`; v4 changes documentation and mapping only, with the same code as v3.

## Native phases and lifetimes

`FRoomScenarioCommand` runs each setup and continuation once on the game thread. While preparation is pending, it returns to Unreal's automation runner. It does not tick the core ticker, drain the task graph or sleep. Standalone fixture worlds receive normal world ticks using elapsed wall time. The fixture keeps room time fixed and submits no fighter input during preparation.

Each setup supplies the selected configuration to an ordinary initialized fixture battle and calls public `BindBattle` before requesting start. The delayed-history configuration retains the original RNG seed of 9009. Pending preparation leaves native actor ticks enabled, including the supplied fixture actor and replacement actors. There is no tick guard and no assumption that player existence completes pending initialization. The fixture submits no fighter input commands during preparation. After public active/new-match success and a usable native battle are observed, it disables automatic ticking for the original manual-input continuation. A synchronous success enters this phase in the same update; pending work returns to the engine normally. Every original confirmed-input/frame assertion remains. The test does not write match identity, frame history, readiness, active state, or implementation storage.

The helper polls public `IsActive` and the current fighter's nonempty match identity. Successors must differ from their previous identity. It reacquires the current world and initialized battle before continuing. It prefers the current world's game state and otherwise finds the initialized native battle in that world. The fixture does not require allocation identity or a fixture battle subclass after travel. Game instances stay rooted across latent phases; cleanup uses the current game-instance world.

Widget controls hold weak connection handles across preparation. If travel destroys a test-owned controller, the test finds the surviving connection by acknowledged membership or creates a normal fixture controller. It recreates the panel and reauthenticates through actual widget actions. It requires nonempty current membership, restored original roles and unchanged fighter assignments. A newly authenticated join generation may use a different membership token. Existing same-connection retry-content membership checks remain unchanged. It then runs the original pause, combat, navigation, export, replay and display assertions. The separate endpoint/travel tests still cover automatic player UI continuity.

## Bounds and validation

Each native preparation has a 30-second wall-time fixture bound. Expiry records a failed setup with the relevant start assertion. It is not a public maximum latency requirement. The Python outer preparation wait is also 30 seconds; an in-flight correlated command retains its existing transport/response timeout, so this is not a strict total wall-time cap. No existing runtime budget, release delay, input count or gameplay assertion was relaxed. The manual native continuations retain their existing frame-by-frame assumptions. If a protected run exposes unconfirmed local simulation during preparation, that scheduling failure must be diagnosed separately; this patch does not reset or rebaseline implementation-owned gameplay state to conceal it. In particular, the zero-input witness still requires an exported empty confirmed-input history. If confirmed pairs occur before an asynchronous success can be observed, the case remains an unresolved scheduling limit and needs an interruption triggered by that public success delivery; it must not be counted as closed or pass with nonempty history. Protected runs must distinguish fixture initialization/transport failures from behavioral failures using their diagnostics.

All 19 top-level Python modules compile and all 17 host checks pass. Host checks cover immediate success, pending-to-active observation without status vocabulary or historical events, and timeout when diagnostic text claims success without the public effect. C++ parses with the declaration and scope-exit macros normalized for the host parser. An assertion inventory retains every original assertion; four accepted-start labels moved into the latent helper, and twelve widget lifetime assertions were added. This is static evidence only. Unreal compilation and execution have not been run locally and require the protected EC2 operator.

The v3 code passed independent test-constraints review for protected compile/runtime with the stated asynchronous scheduling limitation. The v4 refresh corrects the live zero-input guide and mapping, and requires verification that code hashes match v3 before integration. Protected Unreal compilation and execution are still required.
