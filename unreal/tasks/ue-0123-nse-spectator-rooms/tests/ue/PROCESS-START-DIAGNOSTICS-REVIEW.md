# Process fixture start diagnostics

This logging-only proposal layers on the independently approved process-binding-lifetime v1. It does not change `PreparedBattleMatches`, readiness/start results, actor ticks, input commands, assertions or bounds. Delta50's prepared predicate changes from true to false at start while the recorded seed, frame, actor class and current worker world remain unchanged; its other preconditions were not logged, so the cause remains unknown.

Immediately before each actual fixture room start dispatch and after the existing post-dispatch manual-control check, the fixture emits `fixture-start-diagnostic`. It reads the two configured fighter identities through public, read-only `Observe` and records their current membership, assignment, role and match. It then records every native fixture predicate precondition, equality checks against the captured preparation configuration, both player presence/classes, current/prepared actor/world ids, current and captured seed/timer/round count/start delay/training, and fixture preparation/travel flags. Existing Emit supplies the current map, native frame and public active state. A separate `start_request_nonce` avoids confusing these records with correlated deliveries.

The observations can report ordinary synchronous delivery callbacks, so native fixture fields are read afterward using the current world/actor. These are sequential diagnostic observations, not an atomic state transaction. No private candidate state, encoded gameplay payload or source is inspected. No input, native/world tick, retry or reset is introduced. Diagnostics are emitted at the two start-command boundaries, not on every polling heartbeat. Existing rejected/no-dispatch paths still return as before; no after-start record is fabricated when no dispatch occurs.

Validation strips the added diagnostic method and its two calls and reproduces the approved behavior cpp exactly; removing the single method declaration reproduces its header. Both files pass host C++ parsing. All Python/native tests, decoder assertions and existing budgets remain unchanged. No local UE build/run; protected validation and independent review are required. These diagnostics do not themselves establish or explain a failure.
